# Понятные отказы по ресурсам — 02.11.2026

Первый блок нового запроса владельца: объяснить нехватку ресурсов, затем повысить точность ETA и после подключения проверить другой телефон. Сообщения и контролируемые отказы по ресурсам завершены; ETA — следующий отдельный блок.

## Поведение

- Заполненное хранилище при ручной/профильной обработке названо прямо: «Недостаточно места в хранилище телефона для обработки. Освободите место и повторите обработку».
- Отказ по оперативной памяти отличается от места для файлов. Вместо `Unsafe JPEG allocation …`/сырого OOM показаны русская причина и действия: закрыть другие приложения, повторить, при повторном отказе выбрать меньше кадров. При заранее рассчитанном отказе указаны потребность и доступный безопасный бюджет в МБ; потребность округляется вверх, бюджет вниз. Это доступный обработке бюджет, не вся RAM телефона.
- Лимиты/тайлы/пиксельные алгоритмы прежние. Бюджет выбрасывает отдельный подкласс `IllegalArgumentException` с прежними техническими подробностями; границы обработки преобразуют его и OOM в пользовательское сообщение, сохраняют исходную причину, название этапа и семантику отмены. Другие ошибки не объявляются нехваткой памяти.
- В предупреждении камеры свободное и требуемое место вынесены на отдельные строки, есть совет и объяснение возможной ранней остановки. Текст прокручивается; решение «Начать всё равно»/«Отмена» остаётся отдельно.

Основные файлы: [StorageWriteFailure.kt](../app/src/main/java/com/joe6355/astrophoto/StorageWriteFailure.kt), [JpegMemoryBudget.kt](../app/src/main/java/com/joe6355/astrophoto/processing/jpeg/v2/memory/JpegMemoryBudget.kt), [CaptureStorageWarningDialog.kt](../app/src/main/java/com/joe6355/astrophoto/CaptureStorageWarningDialog.kt); обработчики в ManualSequenceAlignment, JpegOrientation, JpegStacker, JpegProcessingScreen и SessionProcessingCoordinator. Новая система записи или восстановления не создавалась.

## Проверки

**53 JVM-проверки прошли:** StackStorageFailureTest9, ManualAlignmentPathSelectionTest12, JpegV2Stage7Test28, TiledManualStackingTest4; без ошибок/пропусков. Включены настоящий объект OOM без расходования heap, запланированный отказ бюджета, причинная цепочка, отмена с вложенным OOM, сохранение названия этапа и неизменность других ошибок.

**7 Android-проверок прошли** на собственном полном AVD Android13/API33: три StackStorageFailureDeviceTest за0,624с и четыре CaptureStorageWarningDialogTest за9,254с. Ручной ENOSPC, профильный ENOSPC и OOM намеренно выброшены из настоящих progress callbacks на новых собственных JPEG64×64. Исходники и сведения совпали по SHA/байтам, временные каталоги удалены, результат не опубликован. После ручного ENOSPC отдельный повтор создал читаемый PNG64×64; удалён только этот собственный URI.

Диск и heap **физически не заполнялись**. Первоначальные UI-проверки выполнялись с системным шрифтом100%; локальный Density2 не принят за доказательство масштаба отдельного Android-окна диалога. Поэтому объявлен и выполнен один дополнительный проход этого случая с **системным шрифтом200%/320dp**, JUnit3,829с. «Отмена» доступна и не запускает съёмку, текст прокручивается, снимок просмотрен. Это новое условие, не повтор прежней полной приёмки.

QA assembleDebug/assembleDebugAndroidTest, целевые JVM и lintDebug: **BUILD SUCCESSFUL за3мин42с**, lint0 ошибок/fatal,14 предупреждений. Новые APK ставились только в собственный эмулятор `AstroPhoto_UI_API33_20261102`/`emulator-5582`; изолированный ADB5042 имеет USB-ограничение `ASTROPHOTO_EMULATOR_ONLY`.
