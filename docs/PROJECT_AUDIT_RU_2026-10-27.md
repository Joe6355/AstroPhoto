### P1 — нет текущего подписанного основного release и проверки его обновления

Текущая конфигурация: **0.9.0-beta.2, versionCode 3**, minSdk 26, targetSdk 36. Release с оптимизацией собирается, но без прежнего `keystore.properties` остаётся **unsigned**. Прежний ключ находится у владельца на ПК; на ноутбуке его нет.

На телефоне проверялась отдельная QA `com.joe6355.astrophoto.qa20261017`. Старые `com.joe6355.astrophoto` и `com.example.astrophoto` не заменялись. Успешная установка отдельного подписанного release в сентябре не является проверкой нынешнего оптимизированного release и обновления старого приложения.

Перед выдачей пользователям нужно собрать кандидата с согласованным package ID, прежней подписью и подходящим versionCode, затем проверить установку **поверх** совместимого пакета с сохранением файлов, внутренних сведений/пометок и активной сессии. Удалять старое приложение для обхода подписи нельзя. Выпуск нового package ID допустим как отдельная установка, но не называется обновлением существующей.

### P2 — неточный отбор соседних сессий при оценке места

`StorageSpaceChecker.kt:90–115`: запрос `RELATIVE_PATH LIKE "$pathPrefix%"` трактует `_` в имени папки как SQL-подстановку, а после чтения нет проверки буквального `startsWith(pathPrefix)`. Две корректно названные папки с одинаковой датой и именами вида `кама_у_речки_10` / `камаXуXречкиX10` могут попасть в один расчёт среднего размера JPEG.

Подтверждено статически и примером SQLite. Последствие — неверная оценка требуемого места/предупреждение. Это **чтение для оценки, а не удаление соседних кадров**: в путях переименования/удаления/ZIP есть отдельные буквальные проверки префикса. Минимальное исправление — такая же проверка перед добавлением размера; затем один целевой тест.

### P2 — запрет операций во время обработки неполон

Основной экран сессии блокирует переименование/удаление сессии, ZIP и MP4 через состояние координатора. Однако кнопка «Результаты обработки» доступна во время обработки (`SessionBrowser.kt:1042–1046`), а `ProcessedResultsScreen` не получает состояние текущей задачи. В нём переименование/удаление/отправка PNG защищены только собственным `operationRunning`, а не `SessionProcessingCoordinator`.

Это подтверждённый по коду пробел в общем запрете из чек-листа. Потеря исходных Lights/Darks или конкретная гонка на телефоне в этом аудите не воспроизводилась. Перед закрытием пункта нужно определить допустимые действия с уже готовыми файлами и проверить запрет конфликтующих операций во всех точках входа, включая возврат на экран после запуска задачи.

### Проверки, без которых готовность выпуска пока не доказана

Это **не список отсутствующих функций или подтверждённых падений**:

1. Короткая сквозная цепочка на текущем оптимизированном кандидате: запуск/разрешения → снимок/серия → готовая сессия → обработка → просмотр 1:1 → Edited → повторное открытие → ZIP с проверкой содержимого/открытием/отправкой → один реальный MP4 с исключением брака.

4. Совместимость: основной реальный телефон — Android 13. Поддержка minSdk 26/targetSdk 36 в настройках сборки не заменяет runtime-проверку на других версиях. Для ограниченной беты допустимо явно указать проверенную модель; широкую совместимость пока не обещать.

## 5. Сохранность данных, Git и перенос между ПК

- На последнем завершённом нативном прогоне контрольные суммы сохранили **1683 прежних общих файла**, **222 доступных внутренних файла** и обе исходные APK. Добавлялись собственные QA PNG; итог тогда — 1693 общих файла. Это историческое доказательство конкретного прогона, а не новое сканирование всего телефона в этом аудите.
- Авторитетные `session-info` и `frame-marks` записываются через временный файл, `fsync` и atomic move с запасным вариантом. При переименовании сведения готовятся до переноса публичных изображений; при сбое предусмотрен rollback. ZIP читает актуальные внутренние сведения. Поэтому одного копирования `Pictures/AstroPhoto` недостаточно для гарантированного переноса всех внутренних пометок между разными package ID.
- Сохранение редактора создаёт новый PNG; основной путь MediaStore использует `IS_PENDING` и удаляет собственную запись при исключении. ZIP/MP4 также очищают свой незавершённый выход. Редактор при OOM может сохранить preview с предупреждением; это ограничение нужно учитывать при проверке качества.
- FileProvider не экспортирован и выдаёт доступ только к `Pictures/AstroPhoto`, `Documents/AstroPhoto/Exports`, `Movies/AstroPhoto`; общего корня `.` нет. Сервисы не экспортированы. В манифесте нет `INTERNET`; аккаунт, облако и сервер не требуются текущим офлайн-сценариям. RAW не входит в согласованный объём.
- В Git нет реального `keystore.properties`, ключей подписи, `local.properties` и APK; есть только пример настроек подписи. Личные текущие фото/артефакты лежат в игнорируемом `artifacts/`. При этом в репозитории уже есть фиксированный JPEG-набор `urban-window-30` и его диагностические материалы: утверждение «в Git вообще нет фотографий» неверно.
- Используется обычный `main` с `origin/main`; отдельной ветки `codex` в текущем списке нет. Автор Git — `Joe6355 <Dudin1918@mail.ru>`. В этом аудите история не переписывалась. Для работы с двух устройств: перед началом fetch/pull только в чистом дереве, после законченного изменения commit/push; при расхождении изучить обе стороны, не применять force push.
- Java/Android SDK, `local.properties` и подпись остаются локальными. Ключ переносится отдельно от Git. Версия из общего репозитория и версия установленной QA — разные идентификаторы; в отчётах нужно фиксировать source SHA, package ID и APK.

## 7. Практический порядок завершения

1. **Исправить контракт CI** вокруг новой маски и прежнего ARGB-replay без ослабления критериев качества; подтвердить прежние эталоны и сохранение новых RGB16-результатов. Затем один полный набор tests + debug/release lint + builds.
2. **Закрыть два небольших недочёта**: точный префикс в оценке места и согласованные ограничения файловых операций при обработке. Проверить затронутые сценарии, без новой настройки фотографии.
3. **Собрать подписанного кандидата** прежним ключом на ПК или после его отдельного безопасного переноса. Проверить обновление с сохранением данных. На ноутбуке продолжать только совместимое `install -r` отдельной QA; исходные приложения не удалять.
4. **Один ограниченный приёмочный проход** по цепочке из раздела 4 на готовых сессиях и тестовых копиях. Полный повтор десятков предыдущих экспериментов не нужен, если исходники соответствующих этапов не менялись и новых отказов нет.
5. **Зафиксировать бету**: source SHA, имя/размер/хеш подписанного APK, package ID/versionCode, проверенная модель, инструкция обновления, известные ограничения. После этого заниматься оставшимися градиентами, маской/слабыми протяжёнными деталями, дополнительными телефонами и рефакторингом.

Критерий готовности первой беты: зелёный полный CI, подписанный проверенный кандидат, сохранность пользовательских сессий при обновлении и успешная основная цепочка сохранения/просмотра/редактирования/экспорта. Процент готовности по количеству галочек здесь не используется: эти условия имеют разную важность.
